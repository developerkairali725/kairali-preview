# kairalicenters.com FAQ schema — the error, its exact cause, and the one-line fix

Google Search Console reported *Unparsable structured data → Incorrect value type* on
`https://kairalicenters.com/ayurvedic-retreat/`. The owner forwarded the alert to Abishek and ops at
14:00 IST; Gaurav escalated it to Sunaj at 15:00 IST. Neither mail names a cause. This one does.

## The cause: WordPress is injecting `<br />` INTO the JSON

The page serves two JSON-LD blocks. Machine-verified from the live HTML:

| Block | Parses? | `<br />` inside |
|---|---|---|
| 1 (theme/plugin generated) | **yes** | 0 |
| 2 (the FAQPage block, 5 Questions) | **NO — fails at character 1** | **41** |

The FAQ block's source has 42 newlines and 41 of them have been rewritten as `<br />` tags *inside
the script element*, starting before the opening brace:

```
<br />
{<br />
  "@context": "https://schema.org",<br />
  "@type": "FAQPage",<br />
```

That is `wpautop` — WordPress's automatic paragraph filter — doing exactly what it does to any
newline in post content. It cannot tell that this particular content is JSON. The result is not
valid JSON at all, which is why Google reports the value type as wrong: it never gets far enough to
read a value.

**This is not a schema-design mistake.** The markup Anupam/Deepu wrote is fine; the CMS corrupted it
on the way out.

## Scope: ONE page, ONE block

Checked live: `/` (2 blocks, 0 corrupted), `/ayurvedic-retreat/` (1 of 2 corrupted), `/about-us/`
(1 block, 0 corrupted). The clean blocks are the ones generated by the theme/plugin; the corrupted
one is the hand-pasted FAQ. So the trigger is the insertion METHOD, not the site.

## The fix (Deepu's hands — production, so not ours; HARD GATE 1)

Re-insert the same FAQ JSON-LD **as a single line with no newlines at all**, inside a Gutenberg
**Custom HTML** block (not a paragraph/classic-editor field). No newlines means `wpautop` has nothing
to convert, and the block survives intact. Nothing about the schema content needs to change.

Durable alternative, if this recurs anywhere else: move JSON-LD out of post content entirely and emit
it from `wp_head` (theme functions or a schema plugin), where content filters never reach it.

Verification after the fix, in order: fetch the page and confirm the block parses as JSON (zero
`<br />` inside any `ld+json` script) → Rich Results Test → request re-indexing in Search Console.
The GSC error clears on Google's next crawl, not immediately.

## Why it is worth fixing rather than ignoring

FAQ rich results are the visible payoff of that markup in search listings. While the block is
unparsable the page gets none of it — the content is being written and maintained for an outcome it
cannot currently produce.

## Dispositions

- The Search Console alert reads as a schema-quality problem, which sends a marketing person hunting for a wrong field, when the real fault is a CMS content filter rewriting valid JSON into invalid JSON on output — a class of bug the reported symptom actively misdirects you away from — **IMPLEMENT** (done: this diagnosis + the exact fix drafted to Deepu, cc Sunaj and Gaurav; execution is Deepu's, production is never ours)
- Any hand-pasted JSON-LD in WordPress post content is exposed to the same `wpautop` corruption, and nothing on the live sites currently detects it — the only reason this one surfaced is that Google complained — **MONITOR** (home: BACKLOG watch row added this report; if a second instance appears, the answer is the `wp_head` route fleet-wide rather than per-page repaste)
