# AHV — the 34-route horizontal overflow at 1024, found and fixed

2026-09-19. Owner instruction: *"Fix it now."*

## What the sweep said, and why that was not enough to act on

`verify-english-candidate.mjs` reports overflow as a boolean — `document.documentElement.scrollWidth > innerWidth + 1`. At 1024 it was true on 34 routes. A boolean names no cause, and the two obvious "fixes" for it are both wrong: widening a container moves the problem, and `overflow-x: hidden` on a wrapper flips the boolean while leaving the offending element exactly as broken, just clipped.

So the first thing built was a measurement, not a patch: `tools/diagnose-overflow.mjs` reads the offending routes out of the sweep's own output (so it can never drift from what CI measured), loads each one at 1024, waits on the runtime's `data-ahv-snapshot-state` readiness signal, and walks the DOM for every element whose right edge crosses the viewport — keeping only the **outermost** offenders, because a wide child pushes its wrapper, its section and its row past the edge too and three of those four are noise.

## The cause: one selector, one arithmetic assumption

All 34 routes are the `article-reader` family. Every offending element is an `<img>`. Every one of them is matched by one rule in `public/design/article-reader.css`:

```css
@media (min-width:1024px) {
  [data-ahv-family="article-reader"] main img:first-of-type {
    width:100vw !important;
    max-width:100vw !important;
    margin-left:calc(50% - 50vw) !important;
    height:clamp(320px,34vw,460px) !important;
    object-fit:cover !important;
  }
}
```

Two faults, compounding.

**1. `img:first-of-type` does not mean "the first image in main."** It means "the first `<img>` among its own siblings". The rule was written for the hero — its own comment says so: *"Full-bleed, with a fixed shape so a 437px letterbox stops being the first thing on the page."* Measured across the family, it matches **506 images on 129 routes**, not 129.

**2. `calc(50% - 50vw)` centres a viewport-wide box on its CONTAINER'S centre, not the page's.** `50%` is half the containing block. The overhang works out to exactly *(container centre − viewport centre)*, so the breakout lands flush at 0→1024 only when the container is itself centred. The article content row is centred (left 31, width 963), which is why the hero always looked right. A card column is not: 224px–547px wide, sitting off-centre inside a grid. There the same arithmetic puts the image **208px to 375px past the right edge of the page** — 149 images across the 34 routes.

This is a regression from `63acad69`, this stylesheet's own first commit, landed earlier the same day. It is not a fault in any owner-supplied design, and it is our code to fix.

What it looked like on `/packages/` — one of the owner's benchmark pages — was two card thumbnails blown up to 1024px wide, overlapping each other, sitting above three card titles that had lost their images.

## The fix

A second rule, in the same file, that keeps the hero rule off every image that is not a hero:

```css
@media (min-width:1024px) {
  [data-ahv-family="article-reader"] main [style*="grid-template-columns"] img:first-of-type,
  [data-ahv-family="article-reader"] main [style*="display: flex"] img:first-of-type {
    width:100% !important; max-width:100% !important; margin-left:0 !important;
    height:auto !important; object-fit:fill !important; border-radius:4px !important;
  }
}
```

A card column exists because an ancestor lays one out, and in this payload that ancestor always carries the layout in its **inline** style. That makes the discriminator structural rather than geometric — no marker in the payload, no DOM pass, no build step.

Selector candidates were measured before one was chosen, across all 129 article routes plus `/cart/` and `/checkout/`:

| candidate | catches the 149 overflowing | touches a hero |
|---|---|---|
| ancestor with `grid-template-columns` | 105 / 149 | — |
| ancestor with `display: flex` | 145 / 149 | — |
| **either of the two** | **149 / 149** | **0 of 127** |
| depth from `main` ≤ 3 | 149 / 149 | 79 heroes lost |
| inside an `<article>` | 44 / 149 | — |

The chosen pair is the only one that is both complete and hero-safe.

## What else it changes, stated plainly

It also catches **99 images that did not overflow**, because their column happened to be centred. These are the same defect measuring as harmless. Two examples, both checked in the browser:

- `/our-story/` — a decorative lotus SVG stretched to 993px and cropped by `object-fit:cover` to a 348px band. After: whole, at its natural aspect.
- `/how-to-reach/` — a body image at 324×348 before, 324×355 after. Effectively unmoved.

They revert to the size the payload's own inline style asks for (`width:100%; max-width:Npx; height:auto`). No hero is affected on any of the 127 routes that have one — that was measured explicitly, not assumed.

## Proof

**Overflow, before → after** (`tools/diagnose-overflow.mjs`):

| width | routes checked | overflowing before | after |
|---|---|---|---|
| 1024 | 34 (the sweep's own list) | 34 | **0** |
| 1280 | 131 (whole family + cart/checkout) | — | **0** |
| 1440 | 131 | — | **0** |

**The owner's pages** (`tools/computed-style-diff.mjs`, 8 pages × 320/1280):

```
15 of 16 page/width pairs byte-identical
CHANGED  /packages/@1280
         main[2]/section[4] rect 38,1409,1203,891 -> 38,1409,1203,703 [height]
         (page height 10926 -> 9284)
```

**This is the one place the "0 of 16" rule cannot be met, and it should not be.** `/packages/` is a benchmark page *and* one of the 34 broken routes — 18 of its images hang 335px off the right edge at 1024. The only change is that those images stop being stretched, so the page gets shorter. Every other benchmark page, including all eight at 320 and `/packages/` itself at 320, is unchanged to the byte. If the owner would rather `/packages/` stay exactly as it is, the fix can be scoped to exclude it — but then it keeps the defect.

**252-route sweep**, 504 states at 320 and 1024, same tool and same accepted baseline as before:

| | before | after |
|---|---|---|
| passed | 426 | **458** |
| failed | 78 | **46** |
| states reporting horizontal overflow | 34 | **0** |

Every one of the 46 remaining failures is baseline drift, not a rendering fault — 40 `h1 != baseline`, 26 `canonical != baseline`, 22 `title != baseline` and 30 `view != baseline` across the same states. Zero broken images, zero page errors, zero off-origin requests, zero responses >= 400, zero iframes. That drift is the stale `FINAL-PORTABLE-504-VERIFICATION.json` already on record; it did not move in either direction here.

## One tool correction, recorded

`diagnose-overflow.mjs` first grouped offending selectors across *all* routes it visited, including ones whose document does not actually scroll — an element can hang past the viewport and be clipped by an ancestor. That printed "3 routes +60px" at 1280 on a family with zero overflowing pages. Fixed: the grouping now counts only routes whose document really overflows. Same class of mistake this session has flagged three times — a generated view drifting from what it claims to describe — this time in a tool I wrote an hour earlier.
